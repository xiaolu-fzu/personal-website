## 二、系统架构

```
┌─────────────────── 浏览器（GitHub Pages，纯静态）───────────────────┐
│  index.html + assets/js/{data,main,analytics,assistant}.js          │
│                                                                      │
│  assistant.js（小洄本体）                                             │
│   ├─ 语料：window.WORKS（22 张项目卡，运行时读取）                     │
│   ├─ 前端检索：卡片级关键词打分 → Top5                                │
│   ├─ 上下文组装：项目总览 + Top5 详情 + 12 轮历史 + 会话备忘            │
│   ├─ Agent 循环：最多 3 轮，每轮一个工具，执行结果回灌                  │
│   └─ 动作执行：切分类 / 开项目卡 / 开链接 / 定位 / 关闭                 │
└──────────────┬───────────────────────────────┬──────────────────────┘

│         Cloudflare Pages Functions（xiaolu-stats.pages.dev）          │
│  chat.js    查询改写 → 知识库检索 → 调模型 → 三层兜底 → 返回 JSON       │
│  suggest.js 专用追问生成（独立一次调用）                                │
│  search.js  知识库检索（FTS5 + LIKE 兜底，支持项目/知识面过滤）           │
│  track.js   埋点（页面/项目/链接），支持按地址排除自己                    │
│  stats.js   统计聚合（token 鉴权）                                     │
│  clear.js   清除统计数据（密码校验，只清 events）                        │
└──────────────┬──────────────────────────────────────────────────────┘
               │

       │  D1（SQLite）   │        │  DeepSeek API         │
       │  events         │        │  LLM_MODEL（可切换）   │
       │  excluded_ips   │        │  = deepseek-flash     │
       │  kb_chunks 601  │        │  （思考模式）          │
       │  kb_chunks_fts  │        └──────────────────────┘
       │  kb_projects 15 │
       └────────────────┘
```

### 关键设计：为什么检索在后端而不是前端
> 前端检索需要把全部语料下载到浏览器（几 MB），而**后端检索前端零负担** —— 浏览器只发几十字节的 query，收回几十 KB 结果。这也是作品集网站"不变重"的原因。

## 三、开发时间线

### 2026-09-22

#### ⓪ 修复「项目无资料时跨项目兜底 → 张冠李戴」（来源：用户反馈）
- **现象**：小洄答完「欧美 AIGC 用户接受度调研」，用户追问「这个项目有具体细节吗」，它却开始讲「**把关 · 数据库接入 Agent**」✗
- **根因**：该项目的文档**没有入库**（数据分析类只收了绝区零那一份报告），于是「项目内检索 0 条」→ 触发我写的**全库兜底** → 命中了「把关」里关于"细节/文献"的切片 → 讲成了把关
- **关键教训**：我曾两轮修复跨项目问题，但**漏了一处调用点**（`if (hits.length < 4 && searchQuery !== question)` 那个兜底忘了传 `projectHint`），所以第一次没修干净
- **修法（三处）**：
  1. **删除**「项目内 0 条就全库兜底」逻辑；
  2. **补齐所有 `searchKB` 调用点的 `projectHint`**（逐条核对过 4 个调用点）；
  3. 项目内无切片时，向模型注入【知识库提示】：「当前讨论的项目是 X，但知识库里**没有**这个项目的文档切片，只能依据卡片资料回答；卡片里也没有的就直说『这部分细节我手头没有，可以翻它的需求/开发文档』，**绝对禁止**改用别的项目的内容」；提示词再补一条同义规则作第三道防线。
- **实测**：同一场景，改后 `kbHits=0`，回答为「这个项目暂时没有更细的文档切片，我只能按卡片信息来说……它跨 YouTube、TikTok、X 三平台、3049 条内容、英德法西语区、含情感分析与风险结构拆解。更细的细节我这边确实没有，但你可以翻它的需求/开发文档」✔
- **✅ 已符合用户要求**：「如果没有具体内容，需要返回『没有找到相关内容』，或者成功为我讲这个项目的内容」。

#### ① 修复「聊几轮之后跑偏 / 说没接到上一条消息」（最重要的 bug，来源：用户反馈）
- **现象**：聊了几轮之后再点追问「这个点子最早是怎么冒出来的」，小洄回答「**我这边没接到你上一条消息**，不确定「这个点子」指哪个项目」，然后去猜 ProListing 和三体
- **用户追问**：「归因一下，是上文的问题还是问题改写的问题」
- **排查方法**：用浏览器探针**拦截每一轮的 `/api/chat` 请求体**，把 `history` 条数、`lastReply` 长度、history 里最后一条助手消息都打出来
- **抓到的真相**（关键数据）：

  | 轮次 | 用户提问 | history 末条助手（= 上一轮回答）|
  |---|---|---|
  | 第 4 轮 | 那关卡设计呢？| 「你没点名是哪个项目，我先按最相关的真菌星域来说…」⚠️ |
  | 第 5 轮 | 这个项目最难的地方？| 「关卡这块，单张固定地图 19 颗星球…」|
  | **第 6 轮** | **这个点子最早是怎么冒出来的** | 「我觉得**《有据》**最难的不是把模型跑起来…」✗✗ |

- **归因结论：是上文的问题，不是改写的问题** —— 第 5 轮就已经答成《有据》了，所以第 6 轮看到的"上一条消息"是讲《有据》的，自然对不上「这个点子」
- **根因**：**项目锁定不稳定**。我的实现是每轮都重新检索，并用 `hits[0].title` **无条件覆盖** `state.currentProject`；而检索对「它 / 这个项目 / 那」这类**指代词是失效的**（查询串里没有任何项目信息），于是命中谁就把当前项目改成谁 —— 聊几轮必然跑偏
- **修法（三处）**：
  1. **前端显式传 `currentProject`** 给后端，后端**最高优先级采用**（前端最清楚这一轮在聊哪个项目）；
  2. **项目锁定更新规则收紧**：含指代词 → **一律沿用**；只有**用户明确点名某个项目**才切换；首次（还没有当前项目）才按检索结果设定。宁可沿用，也不被检索带跑；
  3. 改写器补【**保留新问题意图**】规则：用户问「怎么来的」就必须改写成问来源，**不许用上一轮回答的主题替换用户的新问题**（上一轮在讲"最难"，新问题问"点子怎么来的"，改写结果不能变成"X 最难的地方"）
- **实测对比**（同一个六轮长对话）：

  | 轮次 | 修复前 | 修复后 |
  |---|---|---|
  | 第 3 轮 | 丢失项目 | ✅「你说的应该是**真菌星域**吧？」|
  | 第 4 轮 | 「你没点名是哪个项目」⚠️ | ✅ 真菌星域 |
  | **第 5 轮** | ✗ **答成《有据》** | ✅「关卡设计是真菌星域目前的短板」|
  | **第 6 轮** | ✗「没接到你上一条消息」| ✅ 锁定**真菌星域** |

- **经验**：多轮对话的「话题锁定」不能交给检索去推断 —— **检索只负责找资料，锁定要由状态机明确维护**。

#### ② 修复「跨项目串答案」（最重要的 bug，来源：用户反馈）
- **现象**：点「打开 ProListing 项目卡」→ 再点追问「这想法是怎么冒出来的」→ 小洄讲的是**真菌星域**（Eufloria / 4399 / 孢子战争）
- **排查**：查询改写**正确**（"ProListing 离线记账应用的创意是怎么来的"）、项目识别**正确**（`projectHint: "ProListing"`），但检索返回的 7 条里**混进了真菌星域的切片**
- **根因**：我写的「命中不足 → **全局补检索**」逻辑。ProListing 里讲"想法来源"的切片少，于是从全库补足，把真菌星域那 6 条「灵感来自 Eufloria / 4399」补了进来 —— 它们**字面上更贴合"想法怎么来的"**，模型被带走
- **修法（五处）**：
  1. **锁定项目时绝不跨项目补检索**，改为「在同一个项目内用原问题再搜一次」（换查询、不换项目）
  2. 只有泛问（无项目锁定）时才允许全库补足
  3. 项目内一条都没命中，才做最后兜底
  4. 提示词新增【**项目一致性｜极其重要**】：切片都标了所属项目，只能使用与被问项目一致的切片，混进来的一律不用，宁可回答"没查到"
  5. 检索结果块里显式声明「以上切片均来自「X」项目」
- **效果**：同一问题，改后 `kbHits=8` 全为 ProListing，回答变成「源头是目标人群的真实痛点……记账和计划两块……PRD 写清为谁做……5 位受访者访谈验证」

#### ③ 修复「追问点一轮后就没有下一轮」（来源：用户反馈）
- **根因**：追问由 `/api/suggest` **单独一次调用**生成，失败或超时后被**静默丢弃** → 输入框上方空白
- **修法**：失败**重试一次** → 仍失败给**通用兜底问题** → 连请求都发不出去也兜底。保证每轮都有下一轮可点
- **效果**：连点三轮追问，每轮都有 3 条新追问

#### ④ 模型模式纠正 + 额度可配置（来源：用户提问引发排查）
- **起因**：用户问「我现在的模型是哪个，不是 deepseek v4.1 吗」，并指出「deepseek 就只有一个模型」
- **实测结论**：

  | 模型名 | 返回 model | 耗时 | 推理 tokens | 性质 |
  |---|---|---|---|---|
  | `deepseek-chat`（原用）| deepseek-flash | 1-3s | **0** | **非思考模式** |
  | `deepseek-flash` | deepseek-flash | 2-4s | 300-1100 | **思考模式** |
  | `deepseek-v4-pro` | deepseek-v4-pro | 9-42s | 600-3000 | 思考模式（深但慢）|

- **第二个坑**：`max_tokens` 原设 900，而**思考模式下推理与回答共用同一额度** → 推理吃光后回答为空
- **修法**：
  1. 额度改为可配置：主回答 `LLM_MAX_TOKENS||3000`、改写 `LLM_REWRITE_TOKENS||300`、追问 `LLM_SUGGEST_TOKENS||400`
  2. 模型切到思考模式：`wrangler pages secret put LLM_MODEL` = `deepseek-flash`
  3. 代码保持 `env.LLM_MODEL || 'deepseek-chat'`，随时可用环境变量在"快"与"聪明"间切换
- **效果**：同一问题，切前只复述（"BM25 因为术语精确"），切后给出「60 题里 BM25 92% vs 向量 22%，跟直觉相反；同一架构用在《三体》小说上就必须靠语义检索——代价是嵌入模型与 ONNX，体积 27MB → 0.1MB」

#### ⑤ 新增「查询改写」（Query Rewriting，来源：用户要求）
- **用户要求**：「在输入问题的时候，会将模型最新的回答和我发出的问题一同输入，改写问题后再进行检索和发送大模型」
- **实现**：
  ```
  用户新问题 + 上一轮模型回答
        ↓ ① 改写：还原指代、补全省略 → 独立完整的检索查询 + 识别问题针对的项目
        ↓ ② 检索：优先在识别出的项目内检索（Top8）
        ↓ ③ 生成：检索切片 + 卡片资料 + 问题 → 大模型
  ```
  - 首轮无上文则**跳过改写**（省一次调用）
  - 改写用 `temperature=0`、输出 JSON `{query, project}`
  - 返回 `_debug: {searchQuery, projectHint, rewritten, kbHits, model, reasoningTokens, finish}` 便于验证
- **效果**：实测「它的短期记忆怎么做的？」→ 改写成「《三体》角色扮演 RAG 的短期记忆是怎么实现的？」

#### ⑥ 上下文记忆四层加固（来源：用户反馈"小洄又不记得上下文了"）
- **① 指代识别补齐**：原来正则只认「它们」、**不认单个「它」** → 导致「它是给谁用的呀」接不住
- **② 显式注入当前项目**：每次提问都带上「本次对话当前讨论的项目是 X，用户说『它/这个』都指它，**不要反问用户指哪个**」
- **③ 已执行动作备忘**：记录已打开过的项目/文档，避免重复、让回答更连贯
- **④ 轮次保护**：`state.seq` 递增，过期的异步追问结果直接丢弃
- **另外**：历史从 8 条 → **12 条**

#### ⑦ 追问交互三次改版（来源：用户逐次要求）
| 版本 | 用户要求 | 实现 |
|---|---|---|
| v1 | 「预测对话不要写在回答下面，要在输入框上面」| 追问区移到输入框正上方 |
| v2 | 「点击预测问题后，上一个对话的预测问题不要再显示」| 提问即清空 + 只保留最新一组 |
| v3 | 「都改成这个格式，而且不要写（标题）」| 与新手推荐问题**同款虚线胶囊**；移除「你可能还想问」标题 |

#### ⑧ 追问方向改版（来源：用户逐次要求，共四版）

| 版本 | 用户要求 | 三条方向 |
|---|---|---|
| v1 | 初始设计 | 深入细节 / 换个角度 / 立刻可做 |
| v2 | 「不要过分深挖产品细节，要简单点的问题或跳转请求」| 简单了解 / 相邻对比 / 跳转请求 |
| v3 | 「一个请求问题 + 一个技术细节问题 + 一个随机问题」| 请求 / 技术细节 / 随机 |
| **v4（最终）** | 「固定一个命令请求，固定一个带有明确名字的其他项目，固定一个当前项目的细节（根据回答内容来）」| **命令请求 / 点名其他项目 / 当前项目细节** |

**v4 的关键设计**：
1. **命令请求** —— 让助手去执行动作（打开需求文档 / 带我去看原型 / 在线玩一下），必须用当前项目真实存在的 links，不重复已执行动作；
2. **点名「其他项目」** —— **必须写出另一个项目的真实名字**（从【全部项目】清单里挑一个不同且有关联/可对比的），**禁止**「别的项目」这类泛指。为此前端新增传参 `allProjects`（22 个项目名），后端拼进提示词的【全部项目】区；
3. **当前项目的细节** —— **必须基于助手这次回答里出现过的具体内容**（数字、机制、决策、文档名），不许问回答里没提过的。

**实测**（两个案例）：
- 背景「有据的访谈怎么做」→ ① 打开有据的需求文档 ② **把关**是怎么拦数据库的 ③ 那 **13 条痛点**是怎么编的；
- 背景「真菌星域试玩发现的问题」→ ① 带我去看看在线原型 ② **果宝特攻**那个怎么做 ③ **U1–U4 的优先级**怎么排的。

**价值**：第 2 条把访客**从当前项目引向另一个作品**，形成「项目之间的横向导览」；第 3 条保证追问「咬得住」当前回答，不会空泛。

**🎯 追问返回空的真正原因：思考模式吃掉了额度（来源：用户一句精准的猜测）**：
- **用户判断**：「大模型返回为空，是不是因为对于预测问题你也用了思考模式」—— **完全正确**。
- **机制**：追问接口模型为 `deepseek-flash`（**思考模式**）而 `max_tokens` 只有 **400**；思考模式下**推理过程与正文共用同一额度**，推理一吃就是 300~400 tokens → 正文为空 → 前端只能兜底 ✗。查询改写（300 tokens）同理。
- **我犯的错**：把「思考模式」一刀切应用到全部三个接口，但**追问与改写根本不需要深度推理**，它们要的是**快和稳**。
- **修法（按任务分开配置）**：

  | 接口 | 模型 | 理由 |
  |---|---|---|
  | 主回答 | `LLM_MODEL`（思考模式 deepseek-flash）| 需要推理深度，值得等 2~4 秒 |
  | 生成追问 | **`LLM_MODEL_FAST`（非思考 deepseek-chat）** | 辅助生成，要快、要稳、不能被推理吃额度 |
  | 查询改写 | **`LLM_MODEL_FAST`（非思考）** | 同上 |

- **实测（5 种输入，含极短输入）**：**5/5 全部稳定返回 3 条** ✔
  - 「那把关呢？」→ 打开把关的需求文档 / 有据和把关有什么不一样 / **为什么只给 10 个结构化工具**
  - 「有据为什么用 BM25？」→ 打开有据的需求文档 / **把关的检索怎么做** / **向量为什么只有 22%**
  - 「打开它的开发文档」→ 带我去看看在线原型 / 把关和它有什么不一样 / **检索方案当初怎么选**
  - **「嗯」**（几乎无信息）→ 打开有据的需求文档 / 把关和它有什么不一样 / **检索方案当初怎么设计的**
  - 修复前「那把关呢？」与「嗯」都是 **0 条**。
- **经验**：**思考模式只该给"需要推理"的任务**。辅助类调用（改写、追问、分类、摘要）应走非思考模式 —— 否则推理会吃掉输出额度，表现为"返回空"，而且很难从日志看出原因。

**🐞 多轮后追问退化成固定的三条老问题（来源：用户反馈附截图）**：
- **现象**：多轮对话后，预测问题一直是「你还有别的项目吗？/ 哪个项目最能体现数据分析？/ 有哪些能直接玩的？」
- **排查**：跑 10 轮长对话并拦截每个请求 → **全部 HTTP 200，没有失败**，但第 2、4、7、8、10 轮的追问都是**兜底模板**（格式「打开 X 的需求文档」，还带空格）
- **三个叠加原因**：
  1. **旧文案残留**：`fallbackAnswer()`（请求失败时的离线降级路径）里仍写着那三条老问题；
  2. **suggest 在"信息量少"的轮次返回空**：实测「那把关呢？」配 24 字的短回答 → **返回 0 条**，于是掉进兜底；
  3. **兜底模板的"其他项目"固定取第一个不同分类的项目** → 永远是「绝区零 2.7」；
  4. 另外 suggest 收不到「当前项目」，信息少时无从下手。
- **修法**：
  1. 离线降级的老三问替换为三方向模板；
  2. suggest 提示词加硬性要求：「**必须输出 3 条，永远不要输出空数组**；信息不足时也要基于【正在讨论的项目】给出三条最基础也最关键的问题」；
  3. 前端补传 `currentProject`（首轮与重试两条路径都要传）；
  4. 兜底模板的"其他项目"改为**随机挑**（不再固定绝区零）。
- **实测**：「它最难的在哪？」+ 把关项目 → ✔ 三条：「打开把关的需求文档 / 有据和把关有什么不一样 / **假阳性漏测是怎么权衡**」；
- **经验**：追问这类"辅助生成"要给出**硬性数量要求**（必须 3 条），否则模型在信息不足时会直接返回空，前端就只能兜底，用户看到的就是"千篇一律"。

**🐞 提示词自相矛盾导致追问变笨（来源：用户判断「应该是指令冲突了」）**：
- **现象**：三条职能虽然定下了，但追问依然"笨笨的"，问得很浅
- **根因**：提示词里**同时存在两条互相打架的指令** ——
  - v2 版本留下的一句「**不要深挖技术或产品实现细节**……不要问机制、参数、算法」（虽然主体已删，但残留了「**也不要问太重的参数/公式题**」）；
  - 而 v4 第三条却要求「**针对机制、决策、踩坑追问来历、取舍或实现细节**」。
  模型面对矛盾指令只能两头都收敛 → 产出平庸 ✗
- **修法**：删掉「不要问太重的参数/公式题」，改为明确许可「**问得深一点没关系，不必刻意回避技术细节**」；每条字数上限由 8~16 放宽到 **8~22**（细节追问需要更长）。并顺手排查了 chat.js，确认主提示词里没有同类残留。
- **实测**（背景：有据为什么只用 BM25）：三条变成——
  ① 打开有据的需求文档 ② 把关的检索是怎么做的 ③ **为什么 RRF 融合反而更差**（咬住了回答里的「RRF 等权融合 47%」这个反常数据）✔
- **经验**：**提示词里的「风格约束」和「内容要求」必须彼此兼容** —— 一边说"别问技术细节"、一边说"追问机制细节"，模型只会折中出平庸结果。改版时要回头清理旧版留下的矛盾条款。

**🐞 随后发现的问题（用户反馈「第三轮后的预测问题就没能坚持这个原则」）**：
- **现象**：连点到第 3 轮之后，追问不再保持三条职能，甚至**整轮没有追问**
- **排查**：跑四轮链路实测，第 2 轮追问数 = **0** ✗
- **根因**：那一轮用户点的是「打开它的需求文档」（**动作类**），助手回答是「好的，我先把卡片打开…」这种**动作确认语** —— 几乎没有实质内容，追问生成器拿不到素材；生成的又被去重逻辑过滤，于是彻底为空
- **修法（四处）**：
  1. 前端新增 `state.substReply`：**只记录长度 > 80 字的回答**（动作确认语不记），追问生成优先用它作素材；
  2. 追问请求的 `reply` 字段改为「本轮回答若够长就用它，否则回退到最近一条实质性回答」；
  3. **兜底问题从"通用三问"改为符合三方向的模板**（`templateFollowups()`）：
     ① `打开 <当前项目> 的需求文档` ② `那 <另一个分类的项目> 呢？` ③ `<当前项目> 最难的地方是什么`；
  4. 重试失败与请求失败两条路径都走这个模板。
- **实测（四轮链条，含两轮动作类）**：

  | 轮次 | 追问 |
  |---|---|
  | 第 1 轮（有据的访谈怎么做）| ① 打开有据的需求文档 ② **真菌星域的访谈计划**怎么写的 ③ 为什么检索策略只用 BM25 |
  | **第 2 轮（打开它的需求文档）** | ① 打开 有据 的需求文档 ② 那 **绝区零 2.7** 呢？ ③ 有据 最难的地方是什么 —— **修复前为 0 条** |
  | 第 3 轮（那把关呢？）| ① 打开 **把关** 的需求文档 ② 那 绝区零 2.7 呢？ ③ **把关** 最难的地方是什么 |
  | 第 4 轮（打开它的开发文档）| ① 打开它的需求文档 ② **行研报告自动化**怎么做的 ③ **假阳性为啥比漏测更危险** |

- **经验**：追问的素材必须是「**有实质内容的回答**」—— 动作确认语（"好的，我帮你打开"）不能拿去生成追问，否则必然是空或废话。

#### ⑨ 初始推荐问题换成四条有含金量的（来源：用户指定）
> 「有据」解决了什么问题？／ 我想玩一下真菌荒域，帮我打开。／ 打开 ProListing 项目卡。／ 你一共有多少项目可以展示？

四条分别覆盖：**价值定位 / 可玩体验 / 项目卡导航 / 项目规模**

## 四、设计决策记录

| 决策 | 为什么 |
|---|---|
| **检索用 FTS5 而非向量** | ① 语料只有 601 条切片，规模小；② 项目文档术语精确（"BM25""三级闸门"），关键词匹配足够；③ **与「有据」项目的实测结论一致**（60 题里 BM25 92% vs 向量 22%）；④ 零额外依赖、零嵌入成本 |
| **追问用独立接口而非"顺便生成"** | 模型在回答时"顺便"想追问，注意力被回答占据 → 产出泛泛；参考 vercel/chatbot 的 `requestSuggestions` 思路改为独立调用 |
| **查询改写** | 用户常说「它/这个」，直接检索必然失焦；改写后能锁定项目与真实意图 |
| **项目锁定后不跨项目补检索** | 跨项目补检索会把"字面更贴合但属于别的项目"的资料混进来 → **张冠李戴**（ProListing 答成真菌星域就是这么来的）|
| **模型用思考模式（deepseek-flash）** | 非思考模式（deepseek-chat）只复述，思考模式会给出因果链与取舍分析；实测延迟仅 2-4 秒，可接受 |
| **额度上限可配置** | 思考模式下推理与回答共用 `max_tokens`，写死会因推理吃光导致回答为空 |
| **动作前先跳转再打开** | 直接弹新标签页会让用户不知道链接从哪来；先切分类→滚卡片→展开详情→滑到按钮→再打开，动作链可见 |
| **行为边界：只做打开/关闭/定位** | 助手不该有删除、修改、提交类能力；且**只在用户明确表达执行意愿时才动手**（含"能看看吗"这类委婉说法）|

## 六、踩坑记录（工程经验）

1. **D1 单条 SQL 有长度上限** —— 601 条切片塞进一条 `INSERT` 会报 `SQLITE_TOOBIG`，必须分批（每 40 条一条语句）
2. **中文检索必须分词** —— 整句丢给 FTS5 完全匹配不到；要拆成「整词 + **2-gram** + 3-gram」，只拆 3-gram 会漏掉「访谈」「发现」这类**双字实词**
3. **不要在子代理运行时对共享目录做通配清理** —— 曾误删有据组正在使用的中间文件，导致 `youju.jsonl` 一度被截断为 0 字节
4. **改写 JS 优先用编辑工具而非 Python 中转** —— Python 会把 `\n` 解释成真实换行，导致正则与字符串拼接处语法错误
5. **Cloudflare secret 修改后必须重新部署** 才生效
6. **wrangler 部署记录里的 Source 字段不代表部署内容** —— 判断是否生效要看接口实际行为
