# 小洄知识库 · 切块与清洗规范 v1

> 依据：Firecrawl《Best Chunking Strategies 2026》（递归切分 400–512 tokens、重叠 10–20% 为最佳默认）、
> Pinecone《Chunking Strategies》（块要"足够大以含完整语义、足够小以保证性能"）、AWS Bedrock 层级分块思路。

---

## 一、切块规则（按优先级）

1. **优先按 Markdown 标题层级切**：`#` → `##` → `###` 逐级下降；
   同一小节内容自然聚合，`section_path` 记录完整层级（如 `三、技术方案 > 3.2 检索策略`）。
2. **单块目标长度**：**400–600 字**（中文 1 字 ≈ 1 token）；**上限 800 字**。
   - 不足 400 字但语义完整（如一个定义、一条决策）→ 保持独立，不强并。
3. **超长小节递归切分**：按 段落 → 句子 顺序切，直到 ≤ 上限；**块间保留 10–15% 重叠**
   （重叠内容用于承接上下文，不重复计入字数统计）。
4. **表格：整表成块，绝不横切**。表格前的一行说明并入该块；超过 20 行的表按"表头 + 每 15 行"分块，
   且**每块都重复表头**。
5. **代码块：整块保留**，不截断；代码块前后各留一句上下文说明。
6. **列表（有序/无序）**：同一主题的列表整块保留；超过 15 项的列表按主题分组。
7. **不切**：一句话、一个定义、一条决策，宁可略短也不破坏语义。

## 二、清洗规则（切之前必须做）

| 问题 | 处理 |
|---|---|
| 乱码 / 编码错误字符 | 删除或按上下文修正 |
| 重复段落（复制粘贴造成） | 只保留一份 |
| 超长段落（>500 字无换行） | 按句号/分号拆成多段 |
| 表格错乱（空格对齐丢失） | 重建为 Markdown 表格（`| a | b |`）|
| 目录 / 锚点行（纯链接） | 删除 |
| 页眉页脚 / 页码 / "第 X 页" | 删除 |
| 装饰性分隔（`----`、`====`、纯 emoji 行） | 删除或转为一个标题 |
| 截图占位（`![图](...)`、`见图 X`） | 删除，或改为"（此处原为界面截图）" |
| 大段源码 | 若属于"实现细节"保留**关键片段**（≤30 行）并加说明；其余删除 |
| 敏感信息 | **必须脱敏**：真实姓名 → 受访者 A/B/C；手机号/邮箱/身份证/密钥 → 删除 |
| 无效内容 | 纯待办清单、临时草稿、`TODO`、测试数据 → 删除或标注 |

## 三、切片输出格式（每条一个 JSON 对象，JSONL）

```json
{
  "project_id": "youju",
  "project_name": "有据 · 企业知识库引擎",
  "doc_title": "有据_技术方案与决策记录",
  "doc_type": "开发",
  "section_path": "三、技术方案 > 3.2 检索策略",
  "facet": "技术",
  "title": "为什么只用 BM25 而不用向量检索",
  "text": "（清洗并适度重写后的正文，400-600 字）",
  "keywords": ["BM25", "向量检索", "60题对照实验"],
  "source_file": "project7/RAG/nianbao/docs/有据_技术方案与决策记录.md",
  "ord": 12
}
```

**facet 八类（每条切片必须归入其中一类）**：
| facet | 含义 |
|---|---|
| `定位` | 这是什么、给谁用、解决什么问题 |
| `用户` | 目标用户、访谈发现、用户画像 |
| `功能` | 功能清单、优先级、交互设计 |
| `技术` | 架构、实现方式、技术选型 |
| `决策` | 为什么这么选、放弃了什么、取舍 |
| `指标` | 量化结果、实验数据 |
| `踩坑` | 遇到的问题与修法 |
| `验证` | 评测、试玩、对照实验、验收 |

## 四、重写原则（"处理得漂亮"的关键）

- 允许**适度重写**：把口语化、跳跃、指代不清的原句，整理成**可直接引用的完整表述**；
- 但**不得增删事实**：数字、结论、时间、人名（脱敏后）必须与原文档一致；
- 保留**原作者视角**（这是"我做的项目"，不是第三方评测）；
- 每条切片应当**脱离上下文也能读懂**（把"它""这个方案"补成具体指代）。
